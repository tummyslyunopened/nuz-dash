# Security policy

Nuz-Dash is a self-hosted hobby project. It handles no payments and stores no
passwords, but a running instance does hold things worth protecting: secret
member links (possession = identity), battery saves and save states, uploaded
ROMs, and an admin surface that can read or delete all of it.

## Reporting a vulnerability

**Contact: bucket-pox-depose@duck.com**

- Please email rather than opening a public GitHub issue — public issues are
  fine for hardening *suggestions*, but not for exploitable bugs in a project
  people expose to the internet.
- Include what you found, how to reproduce it, and what an attacker could do
  with it. A proof-of-concept against your **own** instance is welcome; please
  don't test against instances you don't operate.
- This is a spare-time project: reports get a best-effort response, typically
  within a few days. Fixes ship as ordinary releases; there is no bounty
  program.

## Threat model (what the design assumes)

- **Secret links are the only user auth.** Anyone holding an invite or member
  URL is that user. Links are meant to be shared privately, like passwords,
  and can be rotated at any time (self-service) or regenerated by a link
  manager / the host admin.
- **The lobby creator is privileged and protected**: link-manager and
  ROM-manager permissions can be delegated, but the creator's own link and
  permissions can only be changed from the host's admin dashboard.
- **The admin dashboard trusts its transport**: on localhost it is bound to
  127.0.0.1 (optionally gated by authenticator-app 2FA); on a cloud mount it
  sits behind `ADMIN_TOKEN` basic auth **plus mandatory TOTP 2FA** with
  brute-force lockout and single-use codes.
- **BYO ROM by default**: ROM files never reach the server at all — runners
  supply their own copy in their browser and the server stores only a SHA-256
  fingerprint. Hosted-ROM mode is an explicit, warning-gated admin opt-in;
  when enabled, ROMs and saves are served only to authenticated lobby members
  and are excluded from the git repo and releases.

## Hardening checklist for self-hosters

- **Never expose the admin port (4518).** Don't tunnel it, don't port-forward
  it. For remote admin, use the `/admin` mount with a strong `ADMIN_TOKEN`
  over HTTPS — 2FA enrollment is forced on first login there.
- **Enable local admin 2FA** (Server settings) if other people can reach your
  machine or you leave the dashboard open on shared screens.
- **Share links like passwords.** Send invite/member links over private
  channels only; anyone with the link is in. Rotate a link immediately if it
  leaks (everyone can rotate their own).
- **Keep `server/data/` private.** It contains member tokens, saves, ROMs and
  the 2FA secret. It is gitignored — keep it out of backups you share and off
  public object storage.
- **Serve the public app over HTTPS** (the built-in Cloudflare tunnel and
  cloud hosts both do this) so links and session cookies aren't sniffable.
- **Stay current**: run the latest release and a supported Node version;
  security fixes are not backported to older tags.

## Out of scope

- Attacks requiring an already-compromised host machine or filesystem access
  to `server/data/` (that is game over by design for a self-hosted app).
- Denial of service against your own instance.
- The copyright status of ROMs users upload — instance operators are
  responsible for what their lobby plays.
